# Living World

Живой, развивающийся мир для **Svekla SMP**: региональная экология, развитие и упадок поселений,
абстрактная симуляция дикой природы, региональное влияние и летопись мира.

* **Платформа:** Paper `1.21.11` (`api-version: 1.21`), Java 21
* **Сборка:** Gradle (wrapper в репозитории), `./gradlew build`
* **Хранилище:** SQLite (WAL); драйвер подгружается самим Paper через `libraries` в `plugin.yml`
* **Готовый плагин:** [`releases/LivingWorld-1.0.0.jar`](releases/LivingWorld-1.0.0.jar)

---

## Установка

1. Положите `LivingWorld-1.0.0.jar` в папку `plugins/` сервера Paper 1.21.11.
2. Запустите сервер. При первом запуске Paper скачает `sqlite-jdbc` из Maven Central
   (стандартный механизм `libraries`). Если у сервера нет выхода в интернет, положите
   `sqlite-jdbc-3.46.1.3.jar` в `libraries/org/xerial/sqlite-jdbc/3.46.1.3/`.
3. Настройте `plugins/LivingWorld/config.yml` (миры, размер регионов) и при желании `messages.yml`.
4. Примените изменения: `/lwadmin reload`.

> Размер региона (`general.region-size-chunks`) после первого запуска фиксируется в базе.
> Для смены размера удалите `living-world.db`: история и состояние регионов будут сброшены.

## Как это работает (для игроков)

Мир разделён на регионы (по умолчанию 256×256 блоков). Каждый регион помнит, что с ним делали.

| Действие игроков | Последствие для региона |
|---|---|
| Рубят деревья | Падает лесистость, растёт эксплуатация, со временем падает стабильность |
| Деревья растут из саженцев (в т.ч. от костной муки) | Лес восстанавливается, посадившему засчитывается вклад («хранитель природы») |
| Охотятся на **диких** животных | Падает популяция группы животных; при сильном истощении часть естественных спавнов этой группы не происходит |
| Строят, разводят животных, проводят время | Растёт развитие: возникает поселение, затем активное поселение |
| Торгуют с жителями | Поселение может стать торговым центром |
| Уходят из поселения | Через 14 дней (времени работы сервера) поселение пустеет, затем природа его «забирает» |
| Оставляют природу в покое | Лес, животные и стабильность постепенно восстанавливаются |

**Что не наказывается:** фермы (разведённые, заспавненные и названные животные не считаются дикими),
разбор собственных построек из брёвен, добыча руды (вес мал), обычная игра. Плагин **никогда не изменяет
блоки и не трогает постройки игроков**: «заброшенность» — это состояние региона, редкие клиентские частицы
и запись в летописи.

### Состояния региона

`Нетронутая природа → Развивающееся поселение → Активное поселение → Торговый центр`,
а также `Заброшенное поселение` и `Истощённый регион`. Переходы определяются порогами с гистерезисом и
подтверждаются удержанием условия 30 минут, поэтому статус не «мигает».

### Команды

| Команда | Описание |
|---|---|
| `/world` | Состояние мира: регионы по статусам, средняя стабильность, последние события |
| `/world region` | Текущий регион: имя, статус, развитие, характер, влияние, хранители природы, подсказка |
| `/world ecology` | Лес, стабильность, эксплуатация, скорость восстановления, популяции (с трендами) |
| `/world history [all] [страница]` | Летопись региона или всего мира |
| `/world top [developed\|stable\|damaged\|trade\|green]` | Рейтинги регионов |
| `/world name <имя>` | Назвать поселение (может группа, доминирующая по влиянию) |
| `/world hud`, `/world notify` | BossBar региона; ActionBar при входе в регион (настройки хранятся в PDC игрока) |
| `/lwadmin reload\|save\|stats\|inspect\|set\|simulate\|reset\|purge-history` | Администрирование и диагностика |

Псевдонимы: `/lw`, `/livingworld`, `/mir`. Права: `livingworld.use` и `livingworld.name` (по умолчанию всем),
`livingworld.admin` (OP).

## Архитектура

```
me.fokend.livingworld
├── LivingWorldPlugin        — composition root; жизненный цикл, reload, финальное сохранение
├── model/                   — чистые данные (без Bukkit): RegionKey, RegionState, RegionSnapshot,
│                              Accumulators, HistoryEvent, перечисления
├── sim/                     — чистая симуляция (без Bukkit, покрыта тестами)
│   ├── RegionSimulator      — экология, фауна, стабильность, развитие, состояния, влияние, события
│   └── SimClock             — время симуляции = время работы сервера × time-scale
├── config/                  — неизменяемый LivingWorldConfig, Defaults, ConfigLoader (валидация)
├── storage/                 — SqliteStorage (миграции, транзакции), StorageService (1 поток, ограниченная очередь)
├── region/RegionManager     — кэш регионов: ленивая асинхронная загрузка, догоняющая симуляция,
│                              нарезанные по тикам проходы, пакетное сохранение, вытеснение, «спящий» досчёт
├── history/HistoryService   — летопись: кольцевой буфер, буфер несохранённого, лимит событий в час
├── listener/                — наблюдение за вырубкой/посадками/стройкой/охотой/рыбалкой/торговлей
├── player/                  — сессии онлайн-игроков, учёт присутствия
├── ui/                      — Messages (MiniMessage), Format, HudService, Notifier
├── command/                 — /world, /lwadmin
├── integration/             — цепочка резолверов групп влияния, адаптер scoreboard-команд
└── api/                     — LivingWorldApi (ServicesManager), RegionView, Bukkit-события
```

### Ключевые решения

* **Агрегаты вместо блоков и мобов.** События (сломано бревно, из саженца выросло дерево, убито дикое
  животное) лишь увеличивают счётчики в `Accumulators` региона — O(1) на событие. Раз в минуту шаг
  симуляции сворачивает их в показатели. Никакого обхода чанков, блоков или сущностей.
* **Аналитические формулы по `dt`.** Восстановление — экспоненциальное приближение, популяции — точное
  решение логистического уравнения, активность — экспоненциальные скользящие средние. Один длинный шаг
  даёт тот же результат, что много коротких (проверено тестом). Поэтому регионы не обязаны находиться в
  памяти: при загрузке они «догоняют» пропущенное время чистой математикой.
* **Чанки никогда не загружаются.** Биом нового региона определяется один раз и только если чанк уже
  загружен (`World#isChunkLoaded`); иначе профиль `OTHER`. Фоновый досчёт работает только с БД.
* **Время симуляции = время работы сервера.** Остановка сервера на неделю не делает все поселения заброшенными.
* **Потоки.** Весь игровой стейт живёт только в главном потоке. Поток хранилища видит только
  неизменяемые `RegionSnapshot`/`HistoryEvent` и возвращает результаты через планировщик. Bukkit API
  асинхронно не используется (только потокобезопасный `BukkitScheduler#runTask`).
* **Влияние ≠ владение.** Влияние — это репутация присутствия; оно не даёт прав на блоки и территорию.

### Модель данных (SQLite, схема v1)

| Таблица | Содержимое |
|---|---|
| `lw_meta` | `schema_version`, `sim_clock`, `region_size_chunks` |
| `lw_regions` | состояние, экология, популяции (4 группы), EMA активности, итоги, флаги-защёлки |
| `lw_influence` | влияние групп в регионе (не более 16 записей на регион) |
| `lw_stewards` | вклад игроков в озеленение (не более 16 на регион) |
| `lw_history` | летопись: время, тип, регион, значение, субъект, участники |

Миграции применяются по порядку в транзакции. База **более новой** схемы не открывается (защита от
порчи данных при откате плагина). Повреждённая БД переименовывается в `living-world.db.corrupt-<время>`
(не удаляется), создаётся новая. Значения при загрузке санируются (NaN, выход за диапазон, неизвестные enum).

Почему SQLite: в проекте нет своей БД, а Living World нужны транзакции (атомарное сохранение пакета
регионов и летописи), устойчивость к аварийному завершению (WAL) и выборки для рейтингов и пагинации
летописи. Отдельный сервер СУБД для этого не нужен, а YAML-файлы не дают атомарности и запросов.

## Память и жизненный цикл

| Структура | Ограничение / очистка |
|---|---|
| Регионы в памяти | `cache.max-loaded-regions`; чистые простаивающие выгружаются каждую минуту. Сверх лимита держатся только регионы с несохранённой или ещё не учтённой активностью (они освобождаются после ближайшего шага и сохранения) |
| Загружающиеся регионы | `cache.max-pending-loads`; лишняя активность отбрасывается и считается в `/lwadmin stats` |
| Очередь БД | `cache.storage-queue-capacity`; при переполнении задача отклоняется, данные остаются «грязными» и сохраняются позже |
| Летопись в памяти | `history.memory-recent` + не более 2000 несохранённых записей; в БД — `max-events` и `max-age-days` |
| Память брёвен/саженцев | фиксированные LRU (`placed-log-memory`, `sapling-memory`) с упакованными координатами |
| Сессии игроков | создаются при входе, удаляются при выходе; хранят UUID, а не `Player` |
| Влияние/хранители | ≤16 на регион; вклад за шаг ≤64 участника |
| Резолверы кланов | ≤16; снимаются автоматически при выключении плагина-владельца |

При выключении: задачи отменяются (`TaskManager`), слушатели и сервисы снимаются, BossBar'ы скрываются,
поток хранилища дожидается очереди, затем **все** регионы в памяти сохраняются синхронно, соединение
закрывается, ссылки обнуляются. Статических ссылок на плагин и сервисы нет.

## Интеграция с другими плагинами

Living World не зависит от конкретной клановой системы: по умолчанию группа влияния — это сам игрок.
Клановый плагин (или небольшой плагин-мост) подключается через API:

```java
LivingWorldApi api = Bukkit.getServicesManager().load(LivingWorldApi.class);
api.registerInfluenceResolver(myPlugin, player -> {
    Clan clan = clans.of(player);              // быстрый вызов, без БД и сети
    return clan == null ? null : new InfluenceGroup("clan:" + clan.id(), clan.name());
});
api.recordTrade(player, shopLocation, 1.0);    // сделки магазинов/аукционов игроков
api.regionAt(location).ifPresent(view -> view.stability());
```

События: `RegionStateChangeEvent`, `WorldHistoryEvent` (только для информирования, главный поток).
В конфиге есть необязательный адаптер ванильных scoreboard-команд (`influence.scoreboard-team-adapter`,
по умолчанию выключен).

**Territory Eco-Anomalies.** Living World только моделирует и публикует состояние (`RegionView`:
лесистость, стабильность, эксплуатация, популяции) и ничего не спавнит. Будущий модуль аномалий может
читать эти значения через API и масштабировать свои эффекты, не дублируя экологическую модель.

### Проверка на реальном сервере (Paper 1.21.11 build 132, офлайн-режим, бот на mineflayer)

* Плагин запускается; драйвер SQLite подгружается через `libraries`, схема создаётся.
* Вырубка 18 «природных» брёвен засчитана (лес −18/4000); 3 бревна, поставленных и разобранных игроком, — нет.
* Дерево, выращенное костной мукой игрока, засчитано; игрок отмечен как хранитель, получил влияние.
* Убийство дикой (сгенерированной с миром) овцы засчитано; корова, вызванная командой, — нет.
* Все команды `/world` и `/lwadmin`, ActionBar при входе в регион, BossBar (вкл/выкл), летопись,
  рейтинги, переименование; MiniMessage-инъекция в имени отклонена.
* Данные и сим-время сохраняются после `stop` и перезапуска; после `kill -9` `integrity_check = ok`.
* 30 циклов входа/выхода → 0 сессий; 5 × `/lwadmin reload` → по-прежнему 6 задач.
* 20 002 региона в БД, лимит кэша 300: регионы загружаются, досчитываются, сохраняются и
  выгружаются, в памяти ≤ 200; 400 забытых поселений стали заброшенными; лимит летописи сработал.
  TPS 20.0, MSPT ~0.2 мс в среднем, проход симуляции 64–211 мкс.
* 6 × `bukkit:reload confirm`: ошибок нет; после полной сборки мусора — один `RegionManager`,
  один `StorageService`, одно соединение SQLite, без старых команд, слушателей и задач.

**Не проверено вживую** (покрыто только логикой и unit-тестами): торговля с жителями
(`PlayerTradeEvent`), рыбалка, подавление естественных спавнов, адаптер scoreboard-команд,
многопользовательская нагрузка с реальными клиентами.

## Известные ограничения

* Биом региона определяется один раз — по точке первой активности (регион смешанных биомов получает
  профиль места, где игроки появились впервые).
* Активность в регионе, которому не хватило места в очереди загрузок, отбрасывается (учитывается в
  `/lwadmin stats`). При нормальной нагрузке загрузка занимает миллисекунды.
* При одновременном досчёте большого числа забытых регионов часть записей летописи отбрасывается лимитом
  `history.max-events-per-hour` (защита от лавины), сами переходы состояний при этом сохраняются.
* Влияние распространяется только на соседние регионы, находящиеся в памяти (чтобы не загружать новые).
* Изменение `cache.placed-log-memory`, `cache.sapling-memory` и `cache.storage-queue-capacity` вступает в
  силу после перезапуска. Размер региона менять нельзя без сброса БД.
* Paper удерживает ссылку на последний выключенный экземпляр плагина после `/reload` (ровно один, не
  накапливается); Living World очищает в нём все поля. `/reload` в целом не рекомендуется Paper.
* Брёвна, поставленные игроком, запоминаются в ограниченной LRU-памяти; если их разобрать спустя очень
  долгое время (после вытеснения из памяти), это засчитается как вырубка.
* Сделки между игроками и магазины учитываются только если соответствующий плагин сообщает о них через API.
